# Decisions

Record choices that are consequential, hard to reverse, or likely to be questioned later. Do not use this as a daily activity log.

| Date | Decision | Reason | Alternatives rejected | Revisit when |
| --- | --- | --- | --- | --- |
| 2026-09-03 | Optimize for one credible end-to-end journey and a reliable three-minute demo | Hackathon judging rewards clarity and proof more than incomplete breadth | Broad feature set; sponsor-integration collage | The core journey is proven and schedule has slack |
| 2026-09-04 | Build Payr for independent developers billing crypto-native international clients | Keng has firsthand evidence of the invoicing, currency-access, and receipt problem | Autonomous accounts payable; generic A2A/A2C protocol | Repeated freelancer use is disproven |
| 2026-09-04 | The agent publishes only after explicit approval, uses a separate Gmail-send approval, and leaves payment to the client | Preserves agent value without unsafe publication, email, or spending authority | Agent-controlled payer wallet; approval-free publication/send | Core human-paid flow is proven and additional time exists |
| 2026-09-04 | Treat Payr profiles as authoritative; allow host-agent search suggestions only with approval, sources, and field confirmation | Reduces repeated entry without silently treating public-web data as legal truth | Every field in each prompt; unsourced scraping; automatic persistence | A verified business-identity provider is integrated |
| 2026-09-04 | Keep complete invoice data offchain and publish only a salted commitment plus settlement metadata | Protects business details while preserving tamper evidence and reconciliation | Public invoice record; invoice NFT | A specific disclosure/composability need appears |
| 2026-09-04 | Settle exact native USDC through a minimal Arc contract using a short-lived authorization issued at Pay Now | Enables single-transaction payment, replay protection, deterministic invoice-linked events, and bounded offchain voiding | Direct wallet transfer; escrow; long-lived publication signature; ERC-20 approval flow | Arc testnet behavior invalidates the native-value path |
| 2026-09-04 | Make Payr API/MCP-first and demo it in Claude; keep the web app an operations companion without direct invoice authoring | Avoids building a decorative chat UI or a competing browser workflow while giving the freelancer a place to configure, inspect, and prove agent-created work | Telegram-only agent; custom prompt dashboard; direct web invoice editor; API-only demo | Claude connector cannot be made reliable within its timebox |
| 2026-09-04 | Target Arc DeFi first; gate Privy B2B on a real policy-signer spike; keep Arc mainnet launch and Bazantic conditional | Privy now has a security role as the constrained attestor, but no sponsor integration may outrank the core payment proof | Sponsor collage; mislabeling invoice creation as autonomous spending | Any gated spike fails or core Arc flow is unstable |
| 2026-09-04 | Describe the document as a generic commercial invoice/payment request | Jurisdiction-specific tax compliance is unvalidated and outside the build budget | Global or country-specific tax-compliance claims | Qualified legal/tax review is obtained |
| 2026-09-04 | Denominate and settle invoices in exact USDC only | Avoids exchange-rate, oracle, rounding, and depeg disputes | USD invoice with fixed or live USDC conversion | Multi-currency demand is validated and rate policy is designed |
| 2026-09-04 | Generate a frozen PDF and QR at publication and protect both behind a high-entropy bearer link | Gives the agent/client a portable artifact without exposing invoice contents or raw calldata | Browser-print-only MVP; public human-readable slug; calldata QR | Client identity gating becomes necessary |
| 2026-09-04 | Use Gmail for the approved initial invoice message and Resend only for automated verified receipts | Makes the agent workflow visible while keeping deterministic system email under Payr's control | Payr sends both messages; Gmail must attach arbitrary files | Gmail attachment support is proven and remains reliable |
| 2026-09-04 | Assign an immutable sequential number at publication; correct through void-and-replace | Keeps the PDF, page, commitment, email, and receipt consistent | Edit published invoice in place; draft-time numbering | Legal/accounting review requires another numbering policy |
| 2026-09-05 | Adopt `Commit Ledger` as Payr's web experience and retain the arrow-R monogram with a refined `Payr` wordmark | A document-led, proof-focused system makes immutable invoice and settlement facts legible without copying a generic fintech dashboard | Copying Request's navigation/table treatment; copying Plasma's marketing compositions; crypto-neon dashboard styling; replacing the monogram | Usability testing shows the ledger/proof model obscures the primary task or the brand mark fails production constraints |
| 2026-09-05 | Treat incoming Bills as a future capability hidden from the MVP | Incoming payables add a second workflow and payer persona that the committed vertical slice explicitly excludes | Batch payment; autonomous accounts payable; a visible but nonfunctional MVP Bills screen | The receivables journey is proven and incoming-request demand is separately validated |
| 2026-09-05 | Keep `/` public and place the authenticated console under `/app` | Separates the product story from private operations and removes the existing route collision | Dashboard at `/`; public marketing on another host | A multi-product shell or separate marketing deployment is justified |
| 2026-09-05 | Track all four `assets/brand/` references and preserve them unchanged | The approved monogram has durable source material while production assets can be refined separately | Leave assets untracked; overwrite references in place | Brand ownership or licensing changes |
| 2026-09-05 | Release one coherent integration tranche per merge through a versioned PR and tag the merge commit | Isolated agents need a serialized, reviewable integration point and every protected-main state needs an immutable version | Direct pushes; one PR per micro-ticket; pre-merge tags | Release volume becomes operationally disproportionate |
| 2026-09-05 | Protect `main` and version tags with required CI and merge-commit-only releases | Makes the version invariant enforceable instead of relying on coordinator memory | Unprotected maintainer workflow; squash or rebase releases | The repository adopts a different verifiable release mechanism |
