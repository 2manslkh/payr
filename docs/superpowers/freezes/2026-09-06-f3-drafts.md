# F3 Draft And Revision Contract

Base: `v0.2.0` / `400fe13841cef8d54d0f7cd4ee11d92146ccdb4c`.

R04 implements Task 4.1/4.2 and read-only invoice projections. R05 owns publication, voiding, status/Gmail reconstruction, and the worker crash matrix; R06 supplies real documents/storage/protected routes. This freeze pins the draft slice and the already specified document/storage port without claiming later implementations exist.

## Input And Errors

- The exact partial input and proposed-client wrappers are those in Task 4.1. All objects are strict. Paired `draftId`/`expectedVersion` are required together. Every supplied value is validated before business omissions are considered.
- Reject sender/issuer/sender-profile/payout/payee/invoice-prefix properties at every nesting level as `PROHIBITED_FIELD`, including underscore, hyphen, and case aliases. Other unknown fields, wrong types, missing idempotency keys, and invalid/unconfirmed provenance return `INVALID_INPUT` with bounded field issues; never echo values.
- Accept only `user_provided` and absolute HTTP/HTTPS `web_source` URLs without credentials. Never fetch sources or invent confirmation. The backend accepts `confirmed: true` as the declared confirmation from the authorized caller, not as cryptographic evidence of a human review.
- Normalize trim-safe text, lowercase UUIDs and validated email, and canonical positive USDC decimals. Country codes must be actual uppercase ISO alpha-2 codes. Do not normalize invalid money notation into valid input.
- Limits: 64 KiB request body, depth 32, 100 items, 500-character descriptions, 2000-character memo, 128-character nonblank idempotency key. Item and total atomic amounts must fit positive uint256.
- `MISSING_FIELDS` is HTTP 422 with exactly `{code, draftCreated:false, missingFields:[{path,reason}]}` and no writes. Reasons remain `required | default_unavailable | confirmation_required`; absent business values use `required`, unavailable requested terms use `default_unavailable`. Invalid confirmation wrappers are invalid input, not omissions.
- `VERSION_CONFLICT` (409) returns only code, draft ID, and current version. `IDEMPOTENCY_CONFLICT`, `PROFILE_CONFLICT`, and `DRAFT_NOT_EDITABLE` are 409 codes without snapshots. Cross-tenant/missing records are indistinguishable `NOT_FOUND` (404). Identity/CSRF errors retain the existing F2 envelope.

## Resolution And Revision

- Each new version reloads the authoritative sender profile. The caller never supplies sender identity, payout, or numbering settings. Required sender fields are business/address/contact identity, payout wallet, and invoice prefix; default terms may be null when an explicit due date is supplied.
- Saved client IDs must exist in the workspace. Aliases are trimmed and case-sensitive, matching F2 storage. Simultaneous ID/alias must identify the same record. Unknown aliases with complete confirmed proposals become pending creations; unknown IDs are `NOT_FOUND` even with a proposal. Alias-less complete proposals are valid pending creations with no invented legal identity.
- Revision is a patch over the prior immutable snapshot. Omitted items/dates/memo/client preserve prior values; supplied items replace the whole array, and empty memo clears it. A supplied client selector reloads that selection and resets the previous proposal; proposed-only revisions overlay prior client facts and pending changes. No client row is saved during draft creation or revision.
- Issue date defaults to current UTC date for a new draft only. Due date is explicit, or calculated from saved integer terms only with `useDefaultTerms: true`; explicit due date wins. Revisions preserve a prior due date unless supplied or explicitly recalculated with `useDefaultTerms: true`.
- Dates are valid Gregorian `YYYY-MM-DD`, years 2000..9999. Due date cannot precede issue date. Technical payable deadline is UTC midnight 30 calendar days after due date; overflow is invalid, not rounded or clamped.
- A preview shows all resolved facts, each applied default, client provenance, and the pending client-profile diff. Plain-text preview and canonical JSON are derived from the same snapshot. Publication approval must explicitly reference the returned exact draft version and diff.

## Idempotency And Transactions

- Fingerprint SHA-256 of canonical `{operation:"create_invoice_draft",workspaceId,input:<normalized caller input excluding idempotencyKey>}`. Do not fingerprint freshly loaded profiles, current time, generated IDs, or rendered output.
- After strict request validation and actor authorization, check replay before loading new resolution facts or rejecting a now-stale expected version. Same key/fingerprint returns the original immutable version, even after midnight, profile/client changes, or later revisions. A different fingerprint returns conflict without the original private result.
- The write RPC repeats idempotency checking inside its transaction, locks the draft and authoritative profile/client rows, rejects stale version/profile revisions, appends exactly one version, advances `current_version`, and completes the descriptor atomically. Rejection rolls back the reservation and mutation together.
- Persist only invoice/version UUIDs and a safe state in the idempotency descriptor; the complete snapshot lives on the version, not the descriptor. No number, publication attempt, bearer link, signature, or artifact is created by R04.
- R04 version content is append-only. Add `draft_snapshot jsonb` and ensure duplicated F1 columns agree with it. No new chain/contract binding is required for a draft. Later publication may set only its one-way chain/contract/frozen metadata, without changing the draft snapshot or business facts. Preserve existing frozen-version immutability.
- Use the additive migration `202609040003_draft_functions.sql`. R05 will use `202609040004_publication_functions.sql`; subsequent new migrations take the next unused version. Released migrations are never edited.

## Actor And Repository Boundary

`InvoiceActor` has workspace ID plus exactly one owner wallet or connector ID. Owner calls verify workspace ownership. Connector calls verify token workspace, expiry, revocation, and the appropriate fixed scope; no owner session is fabricated. HTTP drafts currently use F2 cookie authorization and CSRF; Task 9 can call the same canonical service after connector admission.

Every RPC is service-role-only, `SECURITY DEFINER`, empty search path, fully qualified, with explicit grants/revokes and no new public table policies. Parameters common to all RPCs are `p_workspace_id uuid`, `p_owner_wallet text`, `p_connector_id uuid`.

| RPC | Additional exact parameters | JSONB result |
| --- | --- | --- |
| `payr_find_draft_replay_v1` | `p_idempotency_key text, p_request_fingerprint text` | DraftVersion or null; conflict raises |
| `payr_get_draft_context_v1` | `p_draft_id uuid, p_client_id uuid, p_client_alias text` (nullable) | DraftContext |
| `payr_save_invoice_draft_v1` | `p_input jsonb` (DraftWrite) | DraftVersion |
| `payr_list_invoices_v1` | `p_search text, p_commercial_state text, p_limit integer, p_offset integer` | InvoicePage |
| `payr_get_invoice_detail_v1` | `p_invoice_id uuid` | InvoiceDetail or null |
| `payr_get_invoice_overview_v1` | none | InvoiceOverview |

Results use the exact shared TypeScript DTOs. Amounts are decimal strings throughout SQL JSON transport. List queries are bounded to 50 items plus a has-more indicator. Summary state derives from canonical commercial/settlement rules, never frontend payment claims. Existing non-R04 records can be summarized from F1 columns; an absent R04 snapshot is explicit null rather than invented data.

SQL business errors use a fixed message code. Only `VERSION_CONFLICT` may include JSON exception detail with exactly `draftId` and `currentVersion`; the adapter validates these before returning them. Every other provider error/detail is discarded, never logged or reflected.

## HTTP And Console

- `POST /api/invoices/drafts`: owner-session/CSRF authorized, strict bounded JSON, canonical service result or exact draft error. No browser authoring form and no MCP endpoint yet.
- `GET /api/invoices`: scoped search/state/offset with one bounded page; `GET /api/invoices/[id]`: scoped detail/history; `GET /api/invoices/overview`: scoped setup/receivables/attention/latest-settlement projection. All private/no-store/no-referrer.
- `/app`, `/app/invoices`, and `/app/invoices/[id]` are authenticated server-rendered views of the same repository projections, not mock data or an alternate client state model. Browser controls only search/filter/navigate. `Open Claude` remains the creation affordance, with honest MCP-not-ready disclosure.
- Show separate commercial/payment facts, aligned exact amounts, defaults/provenance and pending client changes in read-only detail. No raw bearer links, PDF buttons, publish/void controls, or fake settlement proof. Bills stays absent.
- Preserve DESIGN.md, existing rail/mobile navigation, keyboard focus, 44px controls, and system-font fallback. Local/CI browser verification may use ephemeral local Supabase fixtures; it must not introduce a production auth/data bypass.

## Later Publication Port

The `InvoiceDocumentPort` shape remains the exact Task 4.4 interface. R05 tests a deterministic adapter; R06 implements real PDF/QR byte read-back. Publication descriptors contain only UUID maps, hashes, PDF filenames, and state under the F1 allowlist. Object keys are attempt-specific, for example `workspace/<workspaceId>/invoice/<invoiceId>/<version>/attempt/<attemptId>.pdf`; uploads are create-only and existing bytes must verify before reuse. Raw URLs are materialized only in memory, never persisted. Additional publication RPC signatures freeze before R05 fanout.
